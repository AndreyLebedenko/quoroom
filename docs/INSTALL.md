# Установка и первичная настройка

Всё живёт на одной машине. Человек один раз ставит Quoroom одной командой,
дальше поднимает и опускает стенд теми же скриптами.

Ориентировано на Windows-машину, на которой уже установлены и авторизованы
`claude` (Claude Code) и `opencode` (OpenCode CLI).
Quoroom их не устанавливает, не настраивает и не запускает: сессии
открывает человек, а брокер только разносит сообщения.

Дальше в командах `$AgentsChat` — каталог, куда вы склонировали репозиторий.
Задайте его один раз:

```powershell
$AgentsChat = "D:\AI\AgentsChat"   # подставьте свой
```

## Коротко: одна команда

```powershell
cd $AgentsChat
.\install.ps1 --role server            # сервер: Matrix, Element, брокер
.\install.ps1 --role participant        # участник: клиент и набор для CLI агентов
.\install.ps1 --role both               # обе роли на одной машине
```

На Ubuntu 24.04 то же самое:

```sh
cd /путь/к/Quoroom
./install.sh --role server
./install.sh --role participant
./install.sh --role both
```

Установщик задаёт вопросы, делает свою часть и на шаге, который может сделать
только человек, останавливается с кодом `3` и печатает точную команду. В
терминале часть таких шагов просто спрашивается (имя аккаунта, пароль,
комната), а из скрипта или конвейера - останавливает прогон. Повторный запуск
той же команды продолжает с места остановки: сделанное не переделывается и не
перезаписывается. Подробности ниже, запасной путь «всё руками» - в
[конце файла](#5-ручная-установка-запасной-путь).

Без `--role` установщик спросит роль в терминале; из конвейера или скрипта
роль нужно указать явно, иначе это ошибка с кодом `2`.

### Язык установщика

По умолчанию установщик говорит по-английски: названия шагов, вопросы, отказы,
отчёт и справка `--help`. Ключ `--lang en|ru` выбирает язык, ключ можно ставить
в любое место командной строки, в виде `--lang ru` и `--lang=ru`:

```powershell
.\install.ps1 --role participant                # по-английски
.\install.ps1 --role participant --lang ru      # по-русски
```

```sh
./install.sh --role server --lang=ru
```

Тот же ключ переключает и собственные сообщения `install.ps1` и `install.sh`,
которые они печатают до запуска Python (не найден Python, не найден общий слой
установщика). Скрипты передают установщику все ключи без изменений, включая
`--lang`. Другое значение ключа - ошибка с кодом `2` и английским текстом; сами
скрипты в этом случае остаются на английском и ничего не изобретают, ошибку
сообщает установщик. Язык не влияет на коды возврата, на слово подтверждения
`PURGE` и на записи владения: запись, сделанная в одном языке, читается в
другом.

Известное ограничение: русский блок, который печатают `agentschat install` и
`agentschat login` (клиент и набор, они вне этой правки), остаётся русским
внутри английского прогона - например, при установке роли участника. Это
исправит отдельная карточка `task-client-bilingual`.

## 0. Предварительные требования

### Windows

| Что | Как поставить |
|-----|---------------|
| Docker Desktop с бэкендом WSL2, запущенный | winget install Docker.DockerDesktop |
| Python 3.10 или новее | winget install Python.Python.3.11 |
| uv (или pipx) - ради клиента `agentschat` для участника | winget install astral-sh.uv |
| mkcert - ради локального TLS-сертификата | winget install FiloSottile.mkcert |

Одним вызовом:

```powershell
winget install Docker.DockerDesktop Python.Python.3.11 astral-sh.uv FiloSottile.mkcert
```

Windows PowerShell 5.1 - минимум; на PowerShell 7.x `install.ps1` работает без
изменений.

Права администратора нужны два раза и только человеку: строка в hosts и
установка корневого сертификата mkcert (раздел 1.4).

### Ubuntu 24.04

```sh
sudo apt install python3 python3-venv pipx mkcert libnss3-tools \
    docker.io docker-compose-v2 curl procps git
```

`python3-venv` - ради виртуального окружения сервера, `curl` - ради `start.sh`,
`procps` - ради `pgrep` в `stop.sh`, `libnss3-tools` - ради mkcert.

Нативная Linux-машина в проекте не проверялась, живой сценарий Linux не
выполнялся (путь для Windows человек прошёл вручную 5 октября 2026): функциональные прогоны идут в
одноразовом контейнере `ubuntu:24.04` со своим движком Docker
([tools/linux-container](../tools/linux-container)). Всё, что ниже, на Linux
описано по этой проверке; доверие браузера к сертификату на рабочем столе
Linux остаётся непроверенным.

## 1. Установка одной командой

### 1.1. Роль участника

Нужна, чтобы сессии ваших CLI могли говорить с брокером. Docker не нужна.

```powershell
.\install.ps1 --role participant
```

Установщик: находит `uv` или `pipx`, ставит пакет `quoroom` из этого
репозитория, раскладывает набор для Claude Code и OpenCode по каталогам
пользователя, проверяет, что брокер отвечает, и печатает следующий шаг.
Ключи `--claude` и `--opencode` ограничивают набор одним CLI; без них
установщик спросит, в терминале, а из скрипта возьмёт оба.

Если брокер не отвечает, прогон заканчивается кодом `1` с адресом, на котором
его искали, и причиной отказа - так ловится «роль участника поставлена, а
сервер ещё не поднят».

### 1.2. Роль сервера

```powershell
.\install.ps1 --role server --admin-user <ваш логин в Element>
```

Установщик: проверяет Docker, Compose и mkcert, создаёт `bridge/.venv`,
выпускает сертификат, готовит `docker/.env` и `continuwuity.toml` из примеров,
поднимает инфраструктуру, заводит аккаунт человека и два бота, закрывает
регистрацию, запускает брокер и печатает адрес брокера и адрес Element.

Ключи: `--admin-user` - локальный аккаунт человека в Element, `--room-id` -
идентификатор общей комнаты (см. 1.4).

### 1.3. Обе роли

```powershell
.\install.ps1 --role both
```

Роли независимы: участнику Docker не нужен, серверу не нужны `uv`/`pipx`.
Ключи `--admin-user`, `--room-id`, `--broker-url`, `--claude`, `--opencode`
относятся к своим ролям и друг другу не мешают.

Адрес брокера участника по умолчанию `http://127.0.0.1:8770`; другой адрес
задаётся ключом `--broker-url` и попадает и в CLI, и в плагин OpenCode:

```powershell
.\install.ps1 --role participant --broker-url http://127.0.0.1:8770
```

### 1.4. Человеческие шаги

Установщик их только проверяет и никогда не делает сам и не просит
повышения прав. В терминале он спрашивает их сам, а из конвейера или скрипта
каждый шаг - это остановка с кодом `3` и готовая команда.

**Строка в hosts.** Нужна раньше всего: без неё `agentschat.local` не
резолвится в адрес петли.

```powershell
# Windows, PowerShell от имени администратора
Add-Content C:\Windows\System32\drivers\etc\hosts "`n127.0.0.1 agentschat.local"
```

```sh
# Ubuntu, от root
echo '127.0.0.1 agentschat.local' >> /etc/hosts
```

**Корень сертификата mkcert.** Его выпускает установщик от вашего пользователя,
а в системное хранилище ставит человек - иначе корень окажется не тем, которым
подписан выпущенный сертификат.

```powershell
# Windows
mkcert -install
```

```sh
# Ubuntu, из вашей оболочки, не из root: путь к CAROOT должен остаться
# пользовательским, а команда - выполниться от root. Установщик на этом шаге
# печатает CAROOT="<путь>" mkcert -install (от root); sudo env - один из
# способов выполнить это.
sudo env CAROOT="$(mkcert -CAROOT)" mkcert -install
```

**Аккаунт человека.** Установщик спросит логин в терминале (или возьмёт его из
`--admin-user`) и пароль без эха. Если хотите не вручную, дайте пароль через
переменную окружения `QUOROOM_ADMIN_PASSWORD`.

**Комната.** Её создаёт человек в Element: зайти на `https://agentschat.local`,
создать комнату, пригласить `@claude-code` и `@opencode` (приглашения брокер
примет сам), затем Room settings -> Advanced -> Internal room ID и передать
значение установщику через `--room-id` как есть: оно начинается с `!`.

Пока комнаты нет, установщик печатает эти шаги и ждёт следующего запуска.

### 1.5. Токен регистрации: первый аккаунт

`allow_registration` и `registration_token` у образа Continuwuity не читаются
из переменных окружения, а только из смонтированного
`docker/continuwuity/continuwuity.toml` - поэтому это отдельный файл
(подробности в разделе 5, шаг 5.4).

Особенность свежей базы: **настроенный `registration_token` не работает для
первого аккаунта.** Сервер при каждом старте с открытой регистрацией печатает
свой токен, и вот его-то первый аккаунт и должен принять:

```
using the registration token <выданный-сервером-токен>
```

Второй и третий аккаунты создаются уже настроенным токеном. Установщик читает
выданный токен из `docker compose logs continuwuity` сам, причём только после
того, как настроенный был отвергнут, - вам это делать не нужно; при ручной
установке (раздел 5, шаг 5.4) прочитать его нужно самому.

Другой признак закрытой регистрации: `GET /register/available` отвечает
`{"available": true}` даже при закрытой, поэтому он ничего не доказывает.
Единственный честный признак - отказ при регистрации с `M_FORBIDDEN` "This
server is not accepting registrations at this time."

## 2. Повторный запуск

Та же команда безопасна и полезна:

- сделанное не переделывается и не перезаписывается; уже верное помечается
  «уже сделано»;
- то, что осталось незавершённым (например, остановка на человеческом шаге),
  доделывается;
- файлы, созданные до установщика, проверяются и используются как есть, но
  **не записываются в его карточку**: снятие их не тронет, а отчёт назовёт и
  объяснит, почему они остались;
- расхождение останавливает прогон, ничего не записав: чужой `config.yaml`
  переиспользуется молча, а вот уже занятое значение или чужой токен в
  `continuwuity.toml` дают код `1` с именем файла и строки. На машине, собранной
  руками, установщик вместо правки останавливается с кодом `3` и говорит, что
  должен сделать человек.

Участнику повторный запуск полезен после `git pull`: скиллы и плагин - копии,
`agentschat install` их обновляет. Отчёт в конце прямо говорит, нужен ли
перезапуск открытых сессий.

## 3. Снятие и очистка

```powershell
.\install.ps1 --role server --remove        # снять сервер, данные целы
.\install.ps1 --role participant --remove   # снять участника, данные целы
.\install.ps1 --role both --remove
.\install.ps1 --role both --remove --purge  # снять и удалить данные ролей
```

`--purge` без `--remove` недопустим и даёт код `2`.

### 3.1. Что делает снятие

Сервер: останавливает брокер и контейнеры стенда, убирает контейнеры и сеть
compose, удаляет `bridge/.venv`, **если её создал установщик**. Тома с данными
комнаты, `docker/.env`, `continuwuity.toml`, `bridge/config.yaml`,
сертификаты, сохранённые пароли и состояние брокера остаются.

Участник: снимает набор через `agentschat uninstall`, затем пакет `quoroom`.
Файлы набора, которые вы правили руками, `uninstall` оставляет и называет -
удалить их можно только `agentschat uninstall --force`. Файлы сессий в
`~/.agentschat` остаются.

### 3.2. Что делает очистка

`--purge` дополнительно удаляет данные выбранных ролей: у сервера - тома с
данными комнаты, `docker/.env`, `continuwuity.toml`, `bridge/config.yaml`,
листовые сертификаты, файл сохранённых паролей и состояние брокера; у
участника - файлы сессий с токенами.

Перед первым разрушающим шагом установщик печатает точный список целей и
последствие, и ждёт слово `PURGE`. До этого момента не удалено ничего: вопрос
задаётся до первого шага, а шаги идут после ответа. Отказ, пустая строка и
конец ввода дают код `4` и не меняют ничего. Ctrl+C на вопросе тоже ничего не
удаляет, но кодом `4` не выглядит: это прерывание интерпретатора, он
завершается своим кодом (в PowerShell - `0xC000013A`). Слова из конвейера
подтверждают - это не защита от автоматизации, а защита от промаха.

Очистка ролей изолирована структурно: очистка участника не трогает данные
сервера, очистка сервера не трогает состояние участника.

**Важно про `--claude` и `--opencode`.** Эти ключи сужают только снятие и
установку набора. Файлы сессий с токенами лежат в одном каталоге на всех
агентов, и `--purge` участника удаляет их целиком, даже если вы сузили прогон
одним CLI. Полный список целей печатается до вопроса - прочитайте его.

### 3.3. Что остаётся на месте

- именованные тома compose (при снятии), а при очистке - только если Docker
  недоступен: прогон выходит с кодом `1`, называет оставленные тома и просит
  запустить Docker и повторить;
- корень mkcert: он общий для всех проектов машины, поэтому установщик его не
  трогает; на Linux снять можно только `CAROOT=<путь> mkcert -uninstall` от
  root, и это сломает все прочие сертификаты mkcert, а файлы в CAROOT останутся;
- строка `127.0.0.1 agentschat.local` в hosts;
- скачанные образы: они общие для других проектов; имена и
  `docker image rm <образ>` печатает отчёт;
- логи установщика `bridge/logs/start.log`, `bridge/logs/stop.log` и
  `bridge/broker.log`: карточка снятия не относит их к очистке, отчёт называет
  файлы и даёт команду их удалить;
- репозиторий. Ни снятие, ни очистка его не трогают.

Отчёт после снятия печатает всё оставленное с причиной и команду «поставить
обратно» для вашей платформы.

### 3.4. Машина, собранная руками

На такой машине записей установщика нет, поэтому снятие сервера опускает стенд
и убирает его контейнеры и сеть (это не данные, `start` их создаст заново), а
всё остальное оставляет и называет в отчёте: `continuwuity.toml`, состояние
брокера, файл паролей, тома. Ничего из этого не удаляется, потому что
установщик не знает, кто это создал.

Очистка такой машины спрашивает подтверждение, только если у неё есть цели, но
**всё равно останавливает стенд**: `--purge` подразумевает `--remove`, а
снятие сервера всегда останавливает брокер и опускает контейнеры. Поэтому на
машине, собранной руками, `--role server --remove --purge` с кодом `0` означает
«целей не было, стенд остановлен», а не «ничего не произошло». Поднять стенд
после такого прогона - `start.ps1` или `start.sh`.

## 4. Ошибки и коды возврата

| Код | Что значит |
|-----|-----------|
| 0 | сделано |
| 1 | сбой на шаге: имя шага, причина, что уже изменено этим запуском, и команда повтора |
| 2 | неверные ключи или их сочетание, в том числе неизвестное значение `--lang` |
| 3 | нужен человек: установщик напечатал точную команду и ждёт |
| 4 | человек отказался от `--purge`, ничего не изменено |
| 9 | не найден подходящий Python или общий слой установщика; это код оболочки (`install.ps1` / `install.sh`), а не самого установщика |

Сообщение о сбое всегда называет шаг и говорит, как продолжить: повтор той же
команды продолжает с места остановки. Установщик не удаляет чужое состояние,
чтобы «восстановиться», и не сообщает об успехе при частичной настройке.

## 5. Ручная установка (запасной путь)

Ниже - то, что установщик делает сам, для случая, когда запустить его нельзя
или нужно понять, что именно он делает. Все команды - Windows; на Ubuntu
замените `copy` на `cp`, а `\` на `/`.

### 5.1. Локальное имя сервера

Добавьте в `C:\Windows\System32\drivers\etc\hosts` (редактировать от имени
администратора) строку:

```
127.0.0.1 agentschat.local
```

### 5.2. TLS-сертификат (mkcert)

```powershell
mkcert -install
cd $AgentsChat\docker\caddy
mkdir certs
mkcert -cert-file certs\agentschat.local.pem -key-file certs\agentschat.local-key.pem agentschat.local
```

`mkcert -install` кладёт корневой CA в доверенное хранилище Windows — после
этого браузер будет доверять сертификату для `agentschat.local` без
предупреждений (это нужно проделать на каждой машине, с которой будете
открывать Element Web).

Сертификат выдаётся на ~2 года (максимум, который ещё принимают Chrome/Safari).
Дата истечения и команда для продления записаны в
`docker/caddy/certs/RENEWAL.md` — плюс на этот срок уже поставлено
напоминание.

### 5.3. Переменные окружения

```powershell
cd $AgentsChat\docker
copy .env.example .env
```

`SERVER_NAME` уже равен `agentschat.local`, менять не нужно (и нельзя будет
поменять после первого запуска без пересоздания БД).

### 5.4. Токен регистрации (конфиг-файл, не .env)

У докер-образа Continuwuity `allow_registration` и `registration_token` не
читаются из переменных окружения (в отличие от `server_name`, `address` и
т.п.) — только из смонтированного конфиг-файла. Поэтому отдельно:

```powershell
cd $AgentsChat\docker\continuwuity
copy continuwuity.toml.example continuwuity.toml
```

Откройте `continuwuity.toml` и задайте `registration_token` — любую длинную
случайную строку (`allow_registration = true` уже стоит, не трогайте пока).
Этот файл смонтирован в контейнер через `CONTINUWUITY_CONFIG` в
`docker-compose.yml`.

**Первый аккаунт пойдёт не с этим токеном.** На свежей базе сервер печатает
свой собственный токен, и только его принимает первый аккаунт:

```powershell
cd $AgentsChat
docker compose -f docker\docker-compose.yml logs continuwuity
```

Найдите строку `using the registration token ...` и используйте её для первого
аккаунта из шага 5.6. Второй и третий - уже настроенным токеном. Подробности и
доказательства - в
[.development/bugreports/closed/registration-token-first-account.md](../.development/bugreports/closed/registration-token-first-account.md).

ВАЖНО: не удаляйте заголовок `[global]` в начале файла — у Continuwuity все
ключи конфига лежат внутри этой секции, без неё сервер падает при старте с
`invalid type: boolean, expected a map`.

### 5.5. Запуск инфраструктуры

```powershell
cd $AgentsChat\docker
docker compose up -d
docker compose logs -f continuwuity   # Ctrl+C когда увидите, что сервер поднялся
```

Проверка: `https://agentschat.local` в браузере должен открыть Element Web
(с доверенным сертификатом, без предупреждений, если шаг 5.2 сделан на этой
машине).

Если меняете `continuwuity.toml` уже после первого запуска — контейнер сам
не перечитает файл, нужно `docker compose restart continuwuity`.

### 5.6. Регистрация аккаунтов (2 бота + вы)

Регистрация на сервере сейчас открыта по токену. Проще всего зарегистрировать
все 3 аккаунта скриптом-помощником, который делает двухшаговый Matrix
User-Interactive-Auth за вас:

```powershell
cd $AgentsChat\bridge
python -m venv .venv
.venv\Scripts\pip install -r requirements.txt

# requests (в отличие от браузера и от самого моста) не читает системное
# хранилище сертификатов Windows, поэтому ему отдельно нужен путь к корню
# mkcert — вычисляем один раз в переменную и переиспользуем:
$caRoot = "$(mkcert -CAROOT)\rootCA.pem"

# Пароли ниже — придумайте свои, это учётки только для локального сервера.
# Первым регистрируем ВАШ личный аккаунт: он станет администратором сервера.
# --registration-token для него — значение из лога (шаг 5.4),
# для двух ботов — то, что вы вписали в continuwuity.toml.
.venv\Scripts\python register_account.py --homeserver https://agentschat.local `
    --username andrey --password "..." --registration-token "<токен из лога>" --ca-bundle $caRoot

.venv\Scripts\python register_account.py --homeserver https://agentschat.local `
    --username claude-code --password "..." --registration-token "<...>" --ca-bundle $caRoot

.venv\Scripts\python register_account.py --homeserver https://agentschat.local `
    --username opencode --password "..." --registration-token "<...>" --ca-bundle $caRoot
```

Каждый вызов печатает `user_id` / `access_token` / `device_id` — для двух
ботов сохраните эти три значения, они понадобятся в `bridge/config.yaml` на
шаге 5.8. Для своего личного аккаунта просто запомните логин/пароль — им вы
будете заходить в Element Web как обычный человек.

Если всё равно увидите `CERTIFICATE_VERIFY_FAILED` — скрипт сам подскажет
именно эту команду в сообщении об ошибке. Более грубый вариант —
`--no-verify-ssl` вместо `--ca-bundle` (полностью отключает проверку
сертификата, но для разовой локальной регистрации это приемлемо).

Брокер этой проблемы не унаследует: он основан на aiohttp, а не на requests,
и aiohttp на Windows нормально читает системное хранилище сертификатов —
`verify_ssl: true` в `config.yaml` должен работать сразу после
`mkcert -install`, без аналога `--ca-bundle`.

**После того как все 3 аккаунта созданы**, закройте регистрацию: в
`continuwuity.toml` поставьте `allow_registration = false` и выполните
`docker compose restart continuwuity`.

### 5.7. Создание общей комнаты

1. Зайдите в `https://agentschat.local` под своим личным аккаунтом.
2. Создайте комнату, например `agents` (не обязательно делать её публичной —
   это локальный сервер, публичность ничего не защищает и не открывает
   наружу).
3. Пригласите (Invite) в неё `@claude-code:agentschat.local`,
   `@opencode:agentschat.local`.
4. Принимать приглашения вручную НЕ нужно — брокер сам вступает в комнату
   при старте. Достаточно, чтобы боты были приглашены.
5. Откройте именно нужную комнату (напр. **General**, а не пространство!)
   -> Room settings -> Advanced -> скопируйте "Internal room ID"
   (вид `!AbCdEfGh...:agentschat.local`, начинается с `!`).

   ВАЖНО: `room_id` — это ID самой комнаты, а не имя пространства (space).
   Значение должно начинаться с `!` (внутренний ID) или `#` (алиас комнаты).
   Имя пространства вроде `spacerobots:agentschat.local` НЕ подойдёт —
   брокер не найдёт комнату и будет молча игнорировать все сообщения.

### 5.8. Настройка брокера

```powershell
cd $AgentsChat\bridge
copy config.example.yaml config.yaml
```

В `config.yaml`:

- вставьте `room_id`, полученный на шаге 5.7;
- для каждого агента вставьте `user_id` / `access_token` / `device_id`,
  полученные на шаге 5.6.

Больше там настраивать нечего: режимы доставки (`delivery`) уже проставлены
и менять их не нужно. Файл `config.example.yaml` перечисляет всё, что брокер
читает, и ничего сверх того.

### 5.9. Запуск брокера

Брокер — один процесс на всю систему, не по одному на агента.

```powershell
cd $AgentsChat\bridge
.venv\Scripts\python.exe -X utf8 -m sessionchat.broker --config config.yaml --verbose
```

В логе должна появиться единственная строка вида:

```
БРОКЕР ГОТОВ комната=!AbCdEf...:agentschat.local порт=8770
```

Держите это окно открытым: в нём работает брокер. Регистрации сессий хранятся в
`bridge/state/agentschat.db` и переживают его перезапуск, очередь
недоставленных сообщений - нет. Флаг `--agents claude-code,opencode`
ограничивает список обслуживаемых агентов — удобно, пока вы вводите их по одному.

### 5.10. Подключить чат в любом репозитории

Сессии входят в комнату командой `agentschat` и скиллом `chatlogin`. Ни то,
ни другое не кладётся в репозитории: клиент ставится один раз на машину, и
после этого `/chatlogin` работает в сессии, открытой в любом проекте, —
включая сам Quoroom.

Поставить CLI:

```powershell
uv tool install --editable $AgentsChat\bridge
agentschat --help
```

uv кладёт `agentschat.exe` в `~/.local/bin` (`%USERPROFILE%\.local\bin`).
Если `agentschat --help` отвечает, что команда не найдена, — этого каталога
нет в PATH: `uv tool update-shell` добавит его в PATH пользователя, после
чего откройте новый терминал и перезапустите CLI агентов, чтобы они
унаследовали новый PATH.

Без uv то же делает pipx: `pipx install --editable $AgentsChat\bridge`
(`pipx ensurepath` — аналог `uv tool update-shell`).

Разложить скиллы, команду и плагин по каталогам Claude Code (`~/.claude`) и
OpenCode (`~/.config/opencode`):

```powershell
agentschat install
```

Команда печатает строку на каждый файл и в конце просит перезапустить
открытые сессии: запущенные нового набора не увидят. Ключи `--claude` и
`--opencode` ограничивают установку одним CLI.

Что установщик трогает, записано в `~/.agentschat/kit.json`. Если на месте
файла набора уже лежит чужой файл с другим содержимым, установка отменяется
целиком, ничего не записав, и называет этот файл; перезаписать его можно
только явно, `agentschat install --force`.

**Обновление.** Установка editable, поэтому после `git pull` новый код CLI
работает сразу. Скиллы и плагин — копии, сами они не обновятся: после
каждого `git pull` выполните `agentschat install` ещё раз и перезапустите
открытые сессии. Иначе скиллы будут описывать сессиям прежний CLI.

### 5.11. Проверка

В Element Web под своим личным аккаунтом напишите в комнату:

```
@claude-code привет, представься одним предложением
```

Ответ должен появиться в комнату в течение нескольких секунд. Так же
проверьте `@opencode`.

Если ответа нет — смотрите лог брокера: в нём видно и обращение по HTTP от
сессии, и отказ, если что-то не так.
