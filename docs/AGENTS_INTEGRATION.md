# Интеграция с Claude Code / Codex / OpenCode

> **Отменено.** Описывает, как мост первого поколения вызывал CLI в
> headless-режиме. Брокер CLI не вызывает вообще: сессии открывает
> человек. См. [SESSION_BRIDGE.md](SESSION_BRIDGE.md). Раздел «Контракты» в
> конце документа описывает текущий клиент и не отменён.

Английская версия: [AGENTS_INTEGRATION.en.md](AGENTS_INTEGRATION.en.md).


Мост не «понимает» ни один из трёх инструментов — он просто запускает
CLI в headless/non-interactive режиме с текстом сообщения как промптом,
дожидается завершения процесса и публикует результат обратно в Matrix.
Этот документ фиксирует, что именно подтверждено официальной документацией
на момент написания, а что нужно проверить руками перед тем, как доверять
интеграции реальные задачи.

## Claude Code — подтверждено официальной документацией

```
claude -p "{prompt}" --output-format json --permission-mode auto --permission-prompts none
```

- `-p/--print` — headless-режим.
- `--bare` в рабочей конфигурации не используется. Этот флаг — не подтягивает hooks/skills/MCP/CLAUDE.md из `~/.claude` и текущей
  папки, старт быстрее и одинаковый на любой машине. Из-за этого **в bare
  режиме не читаются OAuth-креды** — нужно, чтобы на машине, где крутится
  мост, была переменная окружения `ANTHROPIC_API_KEY` (см. документацию по
  `--bare`). Если вместо этого хотите, чтобы Claude Code использовал вашу
  обычную подписку/логин, уберите `--bare` из команды в `config.yaml` — тогда
  подтянутся ваши обычные hooks/MCP/CLAUDE.md из домашней папки, что может
  быть как плюсом, так и источником сюрпризов (mост будет неявно наследовать
  всё, что настроено в `~/.claude`).
- `--output-format json` — финальный текст лежит в поле `result` JSON-объекта,
  который печатается в stdout последним. Это подтверждено официальной
  документацией дословно.
- `--permission-mode auto --permission-prompts none` — агент работает без
  вопросов к человеку (никто не подтверждает разрешения в фоне). Это
  осознанный компромисс для автономного бота — проверьте, что `workdir`
  агента (`workspace/claude-code`) не содержит ничего, что жалко сломать.

## Codex CLI — headless-режим подтверждён, JSON-схема — нет

```
codex exec --sandbox workspace-write --skip-git-repo-check --cd "{workdir}" --output-last-message "{tmp}" "{prompt}"
```

- `codex exec "prompt"` — headless-режим, подтверждено.
- `--sandbox workspace-write` ограничивает запись рабочим каталогом и разрешёнными
  временными каталогами. `--skip-git-repo-check` нужен, поскольку рабочие
  каталоги стенда не являются Git-репозиториями. Проверено с CLI 0.153.4.
- `--output-last-message <file>` — «Write agent's final message to file»,
  подтверждено официальной документацией дословно. Это то, что использует
  мост, чтобы забрать финальный ответ (`result_mode: file` в конфиге).
- Флаг `--json` (newline-delimited JSON events) тоже существует и
  подтверждён по названию/назначению, **но точная схема событий (в каком
  поле лежит финальный текст ответа) не была проверена нами вживую** —
  разные вторичные источники называют разные поля. Поэтому мост по умолчанию
  использует `--output-last-message`, а не парсинг `--json`.

**Проверить перед боевым использованием:** запустите
`codex exec --help` и `codex exec --sandbox workspace-write --skip-git-repo-check --cd . --output-last-message out.txt "напиши файл test.txt с текстом hi"`
у себя, чтобы убедиться, что версия Codex, установленная на машине, понимает
именно эти флаги (в CLI есть короткие алиасы и версии отличаются).

## OpenCode CLI — headless-режим подтверждён, JSON-схема — нет

```
opencode run --dir "{workdir}" "{prompt}"
```

- `opencode run "prompt"` — headless-режим, подтверждено официальной
  документацией.
- `--dir` — рабочий каталог, подтверждено.
- Флаг `--format json` существует («raw JSON events»), но, как и у Codex,
  **точная схема (имя поля с финальным текстом) не была проверена нами
  вживую** — поэтому мост по умолчанию берёт обычный текстовый stdout
  (`result_mode: raw_stdout`) и просто снимает ANSI-коды цвета.
- OpenCode также поддерживает постоянный сервер (`opencode serve` +
  `opencode run --attach http://localhost:4096 "prompt"`), что экономит
  время холодного старта при частых сообщениях — не включено в v1
  (`command` в конфиге можно поменять на вариант с `--attach`, если после
  тестирования это даст заметную разницу).

**Проверить перед боевым использованием:** `opencode run --format json "тест"`
у себя и посмотреть на реальную структуру вывода, если решите переключить
`result_mode` на `json_field` для более надёжного и богатого парсинга.

## Общая логика моста (`bridge/matrix_bridge.py`)

1. `mention_only`: сообщение обрабатывается, только если в тексте есть
   упоминание localpart (`@claude-code`) или display name агента, либо
   `m.mentions.user_ids` содержит Matrix ID агента. Также поддерживаются
   настроенные aliases и `@room` при `respond_to_room_mention: true`.
2. `max_replies_per_minute`: если превышен — сообщение просто игнорируется
   (CLI не запускается), в комнату раз в 5 минут максимум шлётся одно
   уведомление о лимите, чтобы не было тишины без объяснений.
3. `timeout_seconds`: если процесс CLI не завершился за это время — он
   убивается, в комнату уходит сообщение о таймауте.
4. Каждое сообщение — **отдельный одноразовый вызов CLI**, без
   `--continue`/`--resume`/`--session`. Агент не видит историю комнаты,
   кроме текста самого входящего сообщения. Это самый простой и предсказуемый
   старт; добавление памяти между сообщениями — следующий шаг (для Claude
   Code и OpenCode есть документированные флаги продолжения сессии; для
   Codex механизм продолжения через `codex exec` не был проверен нами и
   требует отдельного изучения `codex exec --help`).

## Отладка

- Смотрите окно PowerShell соответствующего моста — там `logging` с уровнем
  INFO по умолчанию (`--verbose` для DEBUG) печатает точную команду, которую
  мост запустил, и код завершения процесса.
- Если бот не отвечает вообще — проверьте, что: комната совпадает
  (`room_id` в `config.yaml`), бот состоит в комнате (Join, не только
  Invite), в тексте сообщения действительно есть его localpart/имя (если
  `mention_only: true`).
- Если бот отвечает "(ошибка запуска ...)" — сообщение содержит хвост stderr
  соответствующего CLI, это обычно указывает на неверный флаг для
  установленной версии CLI (см. разделы выше — стоит свериться с `--help`
  локально установленной версии).

Результаты живой проверки и фактические версии CLI — в [VERIFICATION.md](VERIFICATION.md).

## Контракты

Раздел описывает текущий клиент `agentschat` и то, что он читает у брокера, а не
мост первого поколения. Для того, кто подключает платформу агента или пишет
скрипт поверх команд, главное правило такое: **исход команды читается из кода, а
не из предложения.** Предложения на языке комнаты предназначены человеку и
модели; их текст может измениться, а код нет. Устройство отказов брокера и
ответов `status`, `say` и `inbox` - в разделе «Контракты» документа
[ARCHITECTURE.md](ARCHITECTURE.md).

### Язык комнаты

Язык один на комнату: ключ `language` (`en` или `ru`) в `bridge/config.yaml`,
по умолчанию `en`. На нём говорят брокер, клиент и конверт сообщения для агента.
Клиент узнаёт язык из поля `language` ответов брокера (`login`, `wait`, `say`,
`inbox`, `status`) и запоминает его, так что говорит им и тогда, когда брокер
недоступен. Язык комнаты сообщает и строка итога `status`: поле `language`.

### Строка итога

`login`, `logout`, `status`, `say` и `ask` после своих предложений печатают на
stdout ровно одну строку:

```
AGENTSCHAT-RESULT {"command":"login","ok":true,"agent":"claude-code","mode":"listener","reconnected":false}
AGENTSCHAT-RESULT {"command":"login","ok":false,"agent":"claude-code","code":"slot_taken"}
AGENTSCHAT-RESULT {"command":"logout","ok":true,"agent":"claude-code"}
AGENTSCHAT-RESULT {"command":"status","ok":true,"language":"en","sessions":[{"agent":"claude-code","state":"listening","label":"x","registered":"10:00:00","quiet":12},{"agent":"opencode","state":"not_connected"}]}
AGENTSCHAT-RESULT {"command":"say","ok":true,"agent":"claude-code","event_id":"$e","warning":"unaddressed"}
AGENTSCHAT-RESULT {"command":"ask","ok":true,"agent":"claude-code","event_id":"$e","answered":false}
AGENTSCHAT-RESULT {"command":"ask","ok":false,"agent":"claude-code","event_id":"$e","code":"broker_unreachable"}
```

- Формат: префикс `AGENTSCHAT-RESULT`, пробел и один компактный JSON-объект
  (без пробелов после `,` и `:`). Строка только из ASCII: не-ASCII символы (например, русская метка
  сессии) записаны как `\uXXXX`. Порядок ключей фиксирован: `command`, `ok`, затем
  `agent` (у команд, которые его принимают), затем остальное, а у отказа `code`
  последним.
- **Читать нужно последнюю строку с этим префиксом.** В предложениях встречается
  текст, который задали участники (метка сессии в строке `status` и в отказе
  `slot_taken`), и он может выглядеть как строка итога. Настоящая строка всегда
  печатается после всех предложений.
- Предложение отказа идёт в stderr, строка итога - в stdout. Коды выхода
  прежние: 0 при успехе, 1 при отказе или недоступном брокере; `status` и при
  `ok:false` даёт 0.
- Токена в строке нет.
- `wait` и `inbox` строки итога не печатают: их вывод читает модель. Исход
  `wait` - это код выхода (0 - конверт напечатан, 1 - listener остановлен или
  связь потеряна) и рамка.

Ключи при успехе:

| Команда | Ключи после `command`, `ok` |
|---------|------------------------------|
| `login` | `agent`, `mode`, `reconnected` |
| `logout` | `agent` |
| `status` | `language`, `sessions` |
| `say` | `agent`, `event_id`, а при замечании брокера ещё `warning` или `note` |
| `ask` | `agent`, `event_id`, `answered` |

- У `login` вместо идентификатора сессии поля `mode` (способ доставки слота,
  например `listener`) и `reconnected` (`true`, если сессия вернулась к своей
  регистрации). Идентификатора сессии брокер не выдаёт, а токен - секрет и в
  строку не идёт.
- `sessions` у `status` - записи брокера из его ответа `/status`, без поля
  `line` (предложения).
- `warning` и `note` - коды `warning_code` и `note_code` из ответа брокера
  (`unaddressed`, `addressed_to_person`); сами предложения клиент печатает как
  пришли.
- `answered` у `ask`: пришёл ли ответ за таймаут. Тишина - не отказ: сообщение
  доставлено, `ok` равно `true`, код выхода 0.

Отказ: `ok` равно `false`, последним идёт `code`. У `status` поля `agent` нет.
Если `ask` оборвался в ожидании ответа, в строке есть `event_id`: сообщение уже
ушло.

| `code` | Когда | Код выхода |
|--------|-------|------------|
| код брокера (`slot_taken`, `session_not_registered` и другие из раздела «Контракты» документа [ARCHITECTURE.md](ARCHITECTURE.md)) | брокер отказал `login`, `logout`, `say` или `ask` (у `ask` и в ожидании ответа) | 1 |
| `broker_unreachable` | запрос не дошёл до брокера | 1 |
| `not_logged_in` | нет файла с токеном этого агента: `logout` без `--force`, `say` или `ask` | 1 |
| `broker_refused` | ответ не 200 без кода (прокси, собственные 404 и 405 aiohttp) | 1 |
| `nothing_to_send` | `say` или `ask` без текста, без `--file` и без `-` | 1 |
| `envelope_without_text` | `ask`: брокер ответил на ожидание без текста конверта | 1 |
| `unexpected_answer` | только `status`: ответ без списка `sessions` и без кода | 0 |

Клиент сам по коду ничего не решает, только передаёт его в строку.

Плагин OpenCode - один из читателей этой строки: он привязывает сессию вызова к
агенту по строке `login` с `ok:true` и снимает привязку по строке `logout` с
`ok:true`. Отказ ничего не меняет, а русские фразы вывода плагин не читает.

### Рамка `wait` и конверт

Первая строка того, что `wait` печатает при остановке, - рамка вида
`=== AGENTSCHAT: <название> ===`. Префикс `=== AGENTSCHAT: ` и суффикс ` ===`
задаёт код, название берётся из каталога и зависит от языка комнаты. Тому, кому
нужен маркер, не зависящий от языка, надо опираться на префикс. Названия на
английском: `broker connection lost` (связь с брокером потеряна: брокер
недоступен дольше допустимого, код выхода 1) и `listener stopped` (брокер отказал в
ожидании или ответил без текста конверта, код выхода 1); на русском это
`связь с брокером потеряна` и `listener остановлен`.

Конверт для агента брокер собирает сам и отдаёт в ответе `/wait` полем
`rendered`; клиент и плагин его печатают, а не пересказывают. Остальные поля
ответа: `sender`, `kind`, `text`, `event_id`, `stamp`, `depth`, `language`.
**`kind` - код `human` или `agent`**; слово «человек» или «агент» стоит только в
тексте конверта, на языке комнаты. Если окно ожидания кончилось без сообщений,
ответ 204. Ответ без `rendered` клиент считает ошибкой контракта
`envelope_without_text`. Первая строка конверта в английской комнате
`=== AGENTSCHAT: incoming message ===`, в русской
`=== AGENTSCHAT: входящее сообщение ===`. Последняя строка зависит от того,
умирает ли listener при доставке: требование поднять новый listener брокер
добавляет только там, где он действительно умирает; плагину оно не выставляется.
